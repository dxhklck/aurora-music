## 一、项目整体功能与模块划分

### 1.1 技术栈与进程模型

| 项 | 内容 |
| --- | --- |
| 壳 | Electron 40（主进程 + 渲染进程 + 预加载） |
| 渲染 | Vue 3.5 + Pinia + Vue Router，Vite 构建 |
| 语言 | TypeScript 5.9；`as any` / `@ts-ignore` / `@ts-expect-error` 全仓为 0，`any` 只出现在 IPC 边界的监听器签名里 |
| 打包 | electron-builder / NSIS，仅 Windows 产出安装包 |
| 外部运行时 | **无**。长尾音源引擎已完全进程内化，不再依赖 Python / 子进程 |
| 规模 | 111 个源文件：主进程 13,192 行 / 渲染层 12,673 行 / 共享层 1,033 行 / preload 146 行 |

三种进程职责划分：

```
主进程 src/main        网络、文件、窗口、托盘、更新、IPC 服务端
   ↕ contextBridge（78 个通道，单向白名单）
预加载 src/preload      只暴露 AuroraApi 一个对象，不开 node 能力
   ↕ window.api
渲染进程 src/renderer  纯 UI + 播放状态机，不直接碰网络与磁盘
```

渲染层 `nodeIntegration: false`、`contextIsolation: true`。所有网络请求（含音频字节流）都在主进程完成，渲染层通过 `muse://` 自定义协议取流。

### 1.2 主进程模块

| 模块 | 文件 | 职责 | 行数 |
| --- | --- | --- | --- |
| 入口 | `index.ts` | 单实例、协议注册、启动顺序、无头自检/截图模式、退出刷盘 | 231 |
| 窗口 | `windows.ts` | 主窗 / 迷你条 / 桌面歌词 / 音量气泡 四类窗口的形态与位置换算 | 639 |
| 媒体代理 | `protocol.ts` + `media.ts` | `muse://media` 补 Referer/CORS/Range，`muse://local` 读本地文件 | 229 |
| 托盘 | `tray.ts` | 菜单、tooltip、播放命令转发（状态不落主进程） | 152 |
| 更新 | `updater.ts` | electron-updater + GitHub，三级渠道探测（直连 → 两个镜像） | 154 |
| IPC | `ipc.ts` | 78 个通道的 handler 注册与设置副作用分发 | 319 |
| 自检 | `selftest.ts` | 17 项端到端检查，无界面跑 | 344 |

### 1.3 音源层（两种实现，统一接口）

`MusicProvider` 接口只有 5 个方法（search / charts / chartDetail / resolveStream / lyric），能力声明放在 `info.capabilities`，UI 全部据此渲染——新增平台不需要改任何组件。

| 类别 | 实现 | 数量 | 说明 |
| --- | --- | --- | --- |
| 原生适配器 | `netease` / `qq` / `kuwo` / `demo` / `local` | 5 | 直连平台私有接口，快，支持榜单与逐字歌词 |
| 引擎音源 | `MusicdlProvider` + `engine/ts/sources/*` | 15 | 酷狗、咪咕、千千、5sing、波点、街声、B 站、JioSaavn、Jamendo、ccMixter、OpenGameArt、Wikimedia、Audius、FMA、SoundCloud |

引擎音源不是「另一个进程」，而是同进程内 3,344 行的 TypeScript 实现：`http.ts`（会话/重试/Cookie 累积）、`probe.ts`（真实地址探测）、`hls.ts`（分片合并）、`tag*.ts`（ID3/MP4/Ogg 标签写入）、`cache.ts`（token 句柄 + 搜索缓存 + 并发合并）。

### 1.4 服务层

| 服务 | 职责 | 关键设计 |
| --- | --- | --- |
| `catalog` | 搜索、榜单、歌词、取址的统一入口 | 三级缓存 + 跨平台换源（打分阈值 60/70）+ LRCLIB 兜底歌词 |
| `download` | 生产者/消费者下载队列 | 断点续传、指数退避、`.part`、sidecar、标签、落盘恢复 |
| `library` | 本地曲库索引 | 单 JSON 原子写、启动 prune、目录扫描（最深 2 层） |
| `playlists` | 收藏与自建歌单 | 内置收藏夹置顶、按 `platform:id` 去重 |
| `settings` | 设置持久化 | 内存缓存 + 串行原子写 |
| `cover` | 封面补全 | 网易云 → QQ 顺序回退，命中 24h / 未命中 10min 缓存 |
| `qrlogin` / `weblogin` / `cellphone-login` | 三种登录 | 扫码、内嵌浏览器、手机验证码；只落 Cookie，不碰密码 |

| 分组 | 内容 |
| --- | --- |
| 路由（7 条） | `/` 发现、`/search` 搜索、`/charts(/:platform/:id)` 榜单、`/library` 本地、`/favorites` + `/playlist/:id` 歌单、`/downloads` 下载、`/settings` 设置 |

| 状态（6 store） | `app`（音源/设置/提示）、`player`（播放状态机）、`search`、`download`、`library`、`playlists` |
| 内核（5） | `audio`（HTMLAudioElement 封装 + 淡入淡出 + 停滞看门狗）、`wave`（Web Audio 频谱）、`plain`（跨 IPC 的纯对象拷贝）、`error`、`format` |

## 二、关键执行流程与依赖关系

### 2.1 启动

```
registerMediaScheme()            协议必须在 ready 前登记
  → requestSingleInstanceLock()  抢不到锁直接 quit
  → whenReady
      → setAppUserModelId / 菜单（macOS 保留编辑菜单）
      → installMediaProtocol()
      → bootstrapProviders()     注册 5 个原生音源
      → settings.init()          读 settings.json
      → setProviderCookies()     登录态进内存仓库
      → library.load() + scanLocalDirs()
      → playlists.load()
      → registerEngineProviders()  15 个 mdl-* （受 engineEnabled 控制）
      → downloads.load()         恢复未完成任务并 pump
      → registerIpc()
      → initUpdater()            仅打包后的 Windows
      → createMainWindow() → createTray() → registerGlobalShortcuts()
```

依赖方向是单向的：`index → services → providers → engine`，没有任何 service 反向依赖 `ipc` 或 `windows`。唯一的例外是 `tray.ts → windows.ts`（取歌词窗口做解锁兜底），已用注释说明避免循环依赖的做法。

### 2.2 搜索（含流式）

```
SearchView → search store.run()
   → IPC.search {platform, keyword, page, limit, streamId}
       → catalog.search()  命中 searchCache（原生 3min / 引擎 10min）直接返回
           → provider.search()
               原生：一次 HTTP
               引擎：musicdl provider → engine.search()
                        → 15 个源里的 1 个 → BaseSource.search()
                             → 分页 URLs 并发（默认 6 并发，每页 3 条）
                             → 每解析出一首 push → onItem → onPartial
       → win.webContents.send('provider:search-partial', {streamId, items})
   ← search store 校验 streamId 后追加渲染（按 platform:id 去重）
```

### 2.3 播放（含两种自愈）

```
playAt(index)
  → IPC.resolveTrack → catalog.resolveTrack(song, autoSwitch, forceSwitch)
      原平台 resolveStream() 失败且 autoSwitch
        → findAlternative()：原生音源优先、引擎最多试 2 个、总预算 15s
        → pickBest() 打分：同名 60 / 包含 35 / 歌手 +30 / 时长 ±10
  → audio.load(muse://media/?u=...&r=...)
  → 15s 停滞看门狗：第一次同源重取（isRetry），第二次 forceSwitch 跨源
```

### 2.4 下载

```
enqueue → queue（并发 1~4，默认 2）
  → transfer
      本地源：分块复制         HLS：引擎 downloadHls 合并分片
      HTTP：Range 续传 + 二进制流计数
  → uniqueFilePath（同名加 (1)(2)）→ moveFile
  → 歌词 .lrc + .meta.json sidecar
  → writeTags（ID3 / MP4 ilst / Vorbis，失败静默）
  → library.add() → 队列落盘
```

### 2.5 依赖关系图（简化）

```
                 ┌──────────── shared（types / ipc / lyric / api）────────────┐
                 │                                                            │
   renderer ──IPC──▶ main/ipc ──▶ services/catalog ──▶ providers ──▶ engine/ts │
      │                │              │                   │              │     │
      │                │              └──▶ services/cache │              └──▶ http/probe/tag
      │                ├──▶ services/download ────────────┘
      │                ├──▶ services/library / playlists / settings
      │                └──▶ windows / tray / updater
      └──▶ core/audio ──▶ muse:// ──▶ main/protocol ──▶ 上游 CDN
```

## 三、本次发现的问题清单与修复结果

### 3.1 已修复（8 项）

| # | 严重度 | 位置 | 问题 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | **高** | `renderer/stores/player.ts:167` | **连点切歌会播错歌**。`playAt` 里的取址是网络请求（引擎音源数秒），后发的先回、先发的后回，后者会把正在放的那首顶掉；过期请求失败还会触发「自动跳过下一首」 | 引入 `playToken` 序号，`await` 后校验，过期结果直接丢弃；`stop()` 也作废在途请求 |

## 四、潜在风险与未解决项

### 4.1 已知设计取舍（不建议当 bug 修）

| 项 | 现状 | 为什么不改 |
| --- | --- | --- |
| 引擎音源只出 10 条、无分页 | `runSearch` 的 `want` 上限 10，`hasMore` 恒为 `false` | 引擎在搜索阶段就解析真实地址，翻倍召回等于翻倍耗时（5–10s → 10–20s）。宁可少给，不可卡死 |
| HLS 下载无法中断 | 取消只在合并完成后清理文件 | 分片循环由引擎侧控制，要做真取消得给 `downloadHls` 传 `AbortSignal` 并逐片检查 |
| `muse://local` 整文件读进内存 | 一首 100MB 无损 = 一次 100MB 峰值 | 注释已记录：`Readable.toWeb` 在 `protocol.handle` 下有背压恢复丢失，会导致「显示播放中但永久静音」 |
| 标签写入失败静默 | `writeTags` 返回 false，任务仍算成功 | 标签是加分项，不能让一次成功的下载变成失败 |

### 4.2 尚未验证 / 需要真机确认

| # | 风险 | 说明 |
| --- | --- | --- |
| 1 | **自动更新与退出流程的交互** | `installUpdate()` 走 `quitAndInstall()`，而 `index.ts` 的 `before-quit` 会 `preventDefault()` 再 `app.exit(0)`。逻辑上 installer 进程已先拉起，但这条路径**没有实机验证过**（需要真打包 + 真实 Release） |
| 2 | 更新渠道可用性 | `ghfast.top` / `gh-proxy.com` 属第三方反代，随时可能下线；失效时靠 `error` 事件重置 `activeChannel` 再探测 |
| 3 | 引擎侧 15 个音源的上游变更 | 每个源都是爬取/私有接口，平台改版即失效。目前只有「空结果 + 请求失败」这一层能识别成 `blocked`，单源静默失败无法感知 |
| 4 | `npm run dist` 未跑 | 安装包体积、NSIS 产出、图标与签名链路本轮都未验证（要下载 Electron 与打包工具） |
| 5 | 高 DPI 多显示器 | `clampRect` 在「窗口比屏幕还宽」时会把窗口推到屏幕左侧之外（`area.x + area.width - rect.width < area.x`），小屏 + 1320 宽会踩到 |

### 4.3 工程性遗留

| # | 项 | 影响 |
| --- | --- | --- |
| 1 | 渲染层无自动化测试 | 本次修的两个高危 bug（播放/搜索竞态）都在渲染层，只能靠人工复现。`tests/` 只覆盖 shared 与主进程纯函数 |
| 2 | 歌词状态每 250ms 推一次 IPC | 桌面歌词窗口关闭时也在推（主进程侧是 no-op），payload 含完整歌词数组。属于可接受的浪费，但可以按需开闸 |
| 3 | `docs/ARCHITECTURE.md` 与代码存在时差 | 该文档是设计说明，不含本次的两个竞态修复 |
| 4 | Android 残留 | `docs/android_migration_plan.md`、`build/android/` 仍在磁盘但被 `.gitignore` 排除；`release/` 里有 2 个历史 APK。Capacitor 依赖已删，这些是纯静态遗留 |
| 5 | `scripts/` 已纳入类型检查 | 但只在 `npm run typecheck` 里，`npm run build` 不跑它——CI 若只 build 会漏 |

## 五、后续迭代建议与优先级

### P0 · 先补可观测性（1 天内）

1. **给渲染层竞态加回归用例**。`playAt` / `run` 的序号机制可以用纯函数抽出来测（`src/renderer/src/core/latest.ts`），不需要跑 Electron。
2. **把 `npm run typecheck` 接进打包脚本**。`"dist": "npm run typecheck && electron-vite build && electron-builder"`，避免类型错误进安装包。
3. **CI 里跑 `engine:test`**。91 个用例覆盖 15 个源的核心解析，是最便宜的回归网。

### P1 · 稳定性（1–2 周）

4. **引擎单源健康度**。现在只有「整批空 + 有失败」才报错。建议在 `BaseSource.search` 里按源记录成功率（滑动窗口），设置页显示「最近 24h 各源成功率」，坏源自动降权。
5. **HLS 取消**。给 `downloadHlsTo` 加 `AbortSignal`，分片循环每片检查一次，用户取消能立刻停。
6. **实机验证自动更新**。发一个 patch 版本走完整链路：检查 → 下载 → 重启安装。这是唯一无法靠代码审查确认的路径。

### P2 · 体验与结构（1 个月内）

7. **歌词 IPC 按需推送**。主进程记住「歌词窗口是否存在」，渲染层通过一个 `lyric-window:present` 标志决定是否推。
8. **`muse://local` 改流式**。先按 8MB 阈值分流：小文件整读（现状，稳定），大文件走 `createReadStream` + 手动背压。风险在于要真机验证 FLAC 拖动进度条。
9. **清理 Android 静态遗留**。`docs/android_migration_plan.md`、`build/android/`、`release/*.apk` 一起决定去留，避免后来人以为还有移动端。
10. **`docs/ARCHITECTURE.md` 增补「渲染层状态机」一节**。当前文档只讲到主进程，播放/搜索的状态迁移（含本次两个序号机制）没有落笔。

### 判断依据

- 这个项目 90% 的故障来自**上游平台变更**，不是本地逻辑。所以 P1 的第 4 条（单源健康度）收益最高。
- 唯二真正会伤到用户的高危 bug 都是**并发时序**，都在渲染层。所以 P0 第 1 条优先。
- 体积已经不是问题（去 Python 后安装目录减 309MB），继续压体积的边际收益很低。
